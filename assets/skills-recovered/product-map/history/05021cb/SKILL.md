# 需求产品地图

## 目标

把客户原始材料转换成一份可评审、可追溯、可交接的产品结构草案。只输出需求理解和结构，不直接写完整 PRD、视觉方案、代码或技术架构。

## 硬规则（必须遵守）

1. **不补写事实。** 每个关键结论标记为 `[已知]`、`[推断]` 或 `[待确认]`。没有证据时写“未提供”，不要用常识填空。
2. **固定顺序。** 必须依次完成：材料盘点 → 项目理解 → 目标与指标 → 用户路径 → 功能地图 → 页面清单 → 功能清单 → 风险与待确认 → 质量检查。不得跳到页面或功能后结束。
3. **目标先于功能。** 每个一级模块都要能说明服务哪个目标或用户行为；无法对应的模块放入“待确认”，不要强行保留。
4. **保留冲突。** 材料互相矛盾时，列出来源和冲突点；按“用户明确指令 > 已确认方案 > Brief/正式文档 > 会议纪要 > 聊天记录 > 推断”暂定，不要替用户裁决。
5. **结构可追溯。** 使用稳定 ID：目标 `G1`、用户步骤 `J1`、模块 `M1`、页面 `P1`、功能 `F1`、风险 `R1`、待确认 `Q1`。引用来源时使用材料 ID，如 `S1`。
6. **控制规模。** 默认最多 8 个一级模块、20 个页面、40 个功能；超过时合并同类项并说明“待后续细拆”，不得为了凑数量扩写。
7. **覆盖完整路径。** 至少覆盖进入、参与、完成/结果、下一步动作；登录、奖励、分享、支付、异常等只有在材料提及或被列为待确认时才加入。
8. **不泄露思维链。** 只给结论、证据、简短依据和检查结果，不输出隐含的逐步内心推理。

## 输入处理

### 材料优先级

先读取用户本轮明确指令，再按优先级整理材料：

1. 已批准的项目目标、范围或方案
2. 客户 Brief、正式需求文档、合同/招标范围
3. 会议纪要、邮件、访谈记录
4. 即时聊天记录、口头转述、截图 OCR
5. 模型推断（只能标为 `[推断]`）

给每份材料编号 `S1`、`S2`……，记录文件名、类型、日期（如有）、可信度和可用范围。扫描件、截图或无法读取的文件标为“无法验证”，不要假设其内容。

### 缺失信息处理

- 有至少一份原始需求材料即可产出草案；缺失项统一写 `[待确认]`。
- 如果没有任何材料，先输出最小输入请求（项目背景、业务目标、目标用户、平台/周期），不要虚构项目内容。
- 一次结果最多提出 5 个高影响确认问题，并说明每个问题影响哪些 `G/M/P/F`。
- 缺失信息不影响结构时继续；缺失“业务目标 + 核心用户动作”时，将质量状态标为“需确认”或“阻塞”，仍给出已知范围内的最小结构。

## 固定工作流

### Step 0：材料盘点

输出材料表：

| ID | 文件/来源 | 类型 | 关键内容 | 可信度 | 可用范围 |
|---|---|---|---|---|---|
| S1 | 例：客户 Brief | md/pdf | 活动背景、目标 | 高/中/低 | 全部/局部/无法验证 |

把事实拆成短句，保留原意；不要在此阶段设计页面。

### Step 1：项目理解

只填证据支持的字段：

| 字段 | 结果 |
|---|---|
| 项目名称 |  |
| 项目背景/触发原因 |  |
| 一句话定位 | “为谁，在什么场景，通过什么方式，解决什么问题” |
| 目标用户 |  |
| 使用场景 |  |
| 平台/渠道 |  |
| 项目周期 |  |
| 范围内 |  |
| 明确不做/范围外 |  |
| 已知限制 |  |

一句话定位无法由材料确定时写“暂无法确定”，不要生成营销口号。

### Step 2：目标与指标

把每个目标写成“目标—用户行为—衡量方式—证据”：

| ID | 目标（业务/用户/品牌） | 期望用户行为 | 指标或成功信号 | 来源/状态 |
|---|---|---|---|---|
| G1 |  |  | 已提供指标；未提供则写候选指标 `[待确认]` | Sx |

规则：

- 不把“做一个页面”当作业务目标。
- 指标缺失时只能提出候选，如“注册完成率（候选）”，不能伪造数值。
- 每个 `G` 至少关联一个 `J` 或 `M`；无法关联的目标列入 `Q`。

### Step 3：用户路径

用固定 5 段，不足部分写“未提供/待确认”：

| ID | 阶段 | 用户动作 | 系统/内容反馈 | 进入条件 | 完成/退出条件 | 承载页面 | 关联目标 |
|---|---|---|---|---|---|---|---|
| J1 | 进入前 |  |  |  |  |  | Gx |
| J2 | 进入 |  |  |  |  |  | Gx |
| J3 | 参与 |  |  |  |  |  | Gx |
| J4 | 完成/结果 |  |  |  |  |  | Gx |
| J5 | 下一步/再次触达 |  |  |  |  |  | Gx |

随后用一行箭头复述主路径：`进入 → 参与 → 完成/结果 → 下一步`。若存在分支，只保留材料支持的分支，并标注触发条件。

### Step 4：产品功能地图（核心输出）

先确定一个产品根节点，再按“一级模块 → 二级能力 → 用户动作/页面”展开。使用以下格式，不写无依据的技术名词：

```text
产品根节点
├── M1 一级模块（服务 Gx/Jx）
│   ├── 二级能力
│   │   ├── 用户动作
│   │   └── P1 页面承载
│   └── 异常/状态（如材料支持）
├── M2 一级模块
│   └── …
└── M3 数据/运营能力（仅在材料提及或列为待确认时保留）
```

地图检查：

- 每个一级模块写明关联的 `G` 或 `J`。
- 页面承载和功能清单中的 ID 必须能回指地图。
- 不能判断是页面还是后台能力时，标为“承载形态待确认”。
- 不把 Logo、颜色、字体等视觉内容混进功能地图；它们交给品牌解析/视觉设计阶段。

### Step 5：页面清单

从地图逐项转换，不凭空增加页面。每页一行：

| ID | 页面/状态 | 目的 | 进入方式 | 核心内容/动作 | 完成后去向 | 必要状态 | 优先级 | 来源 |
|---|---|---|---|---|---|---|---|---|
| P1 |  |  |  |  |  | 正常/空/错误/未登录等 | Must/Should/Could/待确认 | Sx/Mx |

必要状态只写材料提及或结构上不可避免的状态；无法确认时写 `[待确认]`。页面优先级由“直接支撑目标的最小路径”为 `Must`，不要把所有页面都标成 `Must`。

### Step 6：功能清单

按页面和模块展开可执行的用户/系统能力：

| ID | 功能 | 角色 | 触发 | 输入 | 处理/规则（仅已知） | 输出 | 异常/边界 | 依赖 | 优先级 | 来源 |
|---|---|---|---|---|---|---|---|---|---|---|
| F1 |  | 用户/运营/系统 |  |  |  |  |  |  | Must/Should/Could/待确认 | P?/Mx/Sx |

不要把“支持 AI”“接入会员系统”等技术猜测当成事实；如果材料没有说明，写“依赖与实现方式待确认”。

### Step 7：风险与待确认事项

风险和问题分开列出：

| ID | 类型 | 事项 | 影响对象 | 影响 | 建议确认人/材料 | 优先级 |
|---|---|---|---|---|---|---|
| R1 | 风险 |  | Gx/Px/Fx | 高/中/低 |  | P0/P1/P2 |
| Q1 | 待确认 |  | Gx/Px/Fx | 高/中/低 |  | P0/P1/P2 |

至少检查：目标缺失、目标用户缺失、平台/周期不明、路径断点、登录/权限、奖励或支付、内容/数据来源、第三方依赖、隐私合规、异常状态、指标口径和范围冲突。未被材料触发的项目不要强行列为风险。

### Step 8：质量检查

最后只输出检查结果，不输出推理过程：

| 检查项 | 通过条件 | 结果 |
|---|---|---|
| 目标闭环 | 每个 G 关联 J/M/P/F 或明确 Q | PASS/待确认 |
| 路径完整 | 有进入、参与、完成/结果、下一步 | PASS/待确认 |
| 地图可落地 | 每个 M 有能力和页面/承载形态 | PASS/待确认 |
| 页面可验收 | 每个 P 有目的、入口、动作、出口和必要状态 | PASS/待确认 |
| 功能可执行 | 每个 F 有角色、触发、输入、输出、边界 | PASS/待确认 |
| 证据可追溯 | 关键结论都有 S/M/P/F 来源或 `[推断]` | PASS/待确认 |
| 范围受控 | 没有未经证据支持的模块、指标或集成 | PASS/待确认 |

给出总状态：

- `通过`：没有影响最小路径的未决项。
- `需确认`：可继续讨论，但存在未决项；列出 `Q`。
- `阻塞`：核心目标或核心动作无法确定，不能进入原型设计；只交付已知结构和确认问题。

## 固定输出顺序

每次调用都按下面顺序输出，标题不可省略：

1. `# 需求理解与产品结构设计结果`
2. `## 0. 材料与证据`
3. `## 1. 项目理解`
4. `## 2. 目标与指标`
5. `## 3. 用户路径`
6. `## 4. 产品功能地图`
7. `## 5. 页面清单`
8. `## 6. 功能清单`
9. `## 7. 风险与待确认事项`
10. `## 8. 质量检查`

结尾追加一段 `## 交接摘要`，只包含：项目定位、最小主路径、Must 页面、Must 功能、阻塞问题、适合交给下游 Skill 的文件名。

## 下游交接

- **品牌解析 Skill：** 交接 `项目理解`、目标用户、使用场景、品牌触点和内容约束；不要把视觉结论伪装成已确认品牌规范。
- **原型设计 Skill：** 交接 `用户路径`、`页面清单`、`功能清单` 和必要状态；原型阶段仍以 `Q` 为约束，不能把待确认项当成确定需求。
- **任何下游 Skill：** 同时交接材料表、质量状态和 `Q/R` 清单，确保下游知道哪些内容可信、哪些需要确认。

## 运行提示

默认一次完整运行。材料过多时分两次，但必须保存第一阶段产物并作为第二阶段唯一输入之一：

1. **结构阶段：** Step 0–4，保存 `01-project-structure.md`。
2. **明细阶段：** 读取 `01-project-structure.md`，完成 Step 5–8，保存 `02-page-function-detail.md`。

如果用户要求“只做审计/只输出结构”，仍可执行到质量检查，但不要创建 PRD、设计稿、代码或外部系统变更。
